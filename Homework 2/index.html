HMWK 2: From wallet seed to Ethereum address

Hashing, key derivation and cryptographic primitives in the Ethereum wallet pipeline.

Abstract. This report follows the path from a mnemonic phrase to a checksummed Ethereum address. It describes the role of BIP-39, BIP-32, BIP-44, secp256k1, Keccak-256 and EIP-55, separates key generation, key derivation, public-key cryptography, hashing, checksums and encoding, places the technologies in historical order, explains why Keccak-256 differs from the standardized SHA3-256, and discusses why several primitives are used instead of one. A final section discusses the statistical properties of each step.

1. The pipeline

A wallet turns a list of words into an Ethereum address in a fixed sequence of steps. Each step has its own purpose and uses a different tool.

Mnemonic phrase | BIP-39 (checksum, PBKDF2-HMAC-SHA512) Seed (512 bits) | BIP-32 / BIP-44 (HMAC-SHA512, path m/44'/60'/0'/0/0) Private key (256 bits) | secp256k1 (scalar multiplication, Q = kG) Public key (512 bits: x and y) | Keccak-256, keep the last 20 bytes Ethereum address (160 bits, 40 hex digits) | EIP-55 (case encodes a Keccak-256 checksum) Checksummed address

2. Role of each standard and primitive

BIP-39: mnemonic sentence and seed

BIP-39 turns random entropy into words a person can write down. 128 bits of entropy are extended with a 4-bit checksum (the first bits of the SHA-256 hash of the entropy), giving 132 bits. These are cut into 12 groups of 11 bits, and each group selects one word from a list of 2048 words. With 256 bits of entropy the phrase has 24 words. The seed is then computed with PBKDF2-HMAC-SHA512: the mnemonic is the password, the string "mnemonic" plus an optional passphrase is the salt, and 2048 iterations produce 512 bits. A different passphrase gives a completely different wallet from the same words.

BIP-32: hierarchical deterministic (HD) key derivation

BIP-32 builds a tree of keys from one seed. The master private key and a chain code come from HMAC-SHA512 applied to the seed, with the key "Bitcoin seed". Each child is obtained by HMAC-SHA512 from the parent chain code, the parent key and an index. Indexes from 231 up are called hardened: their derivation uses the parent private key, so a leaked child public key and chain code cannot reveal the parent. A single backup, the seed, therefore recovers every key in the tree.

BIP-44: standard derivation paths

BIP-44 fixes the meaning of each level of the tree: m / purpose' / coin_type' / account' / change / address_index. The purpose is 44. The coin type for Ethereum is 60, registered in SLIP-44. The first Ethereum account is therefore m/44'/60'/0'/0/0, and the second address is m/44'/60'/0'/0/1. Following the same convention lets different wallet programs find the same accounts from the same words.

secp256k1: elliptic-curve public-key cryptography

secp256k1 is the curve y² = x³ + 7 over the prime field with p = 2256 − 232 − 977, the same equation family as the toy example of homework 1. It has a fixed base point G and a group order n close to 2256. The public key is Q = kG, computed with point addition and double-and-add. Going back from Q to k is the Elliptic Curve Discrete Logarithm Problem, which is considered infeasible at this size. The same key pair is used for ECDSA signatures, which prove ownership of an address without revealing the private key.

Keccak-256: the hash function

Ethereum takes the 64 bytes of the public key (x and y, without the 04 prefix of the uncompressed format) and hashes them with Keccak-256. The address is the last 20 bytes of the 32-byte output. Hashing here compresses the key to a shorter value and hides the key until it is used in a signed transaction. It is not a form of encryption, and it cannot be reversed.

EIP-55: mixed-case checksum encoding

An address is 40 hexadecimal digits and has no built-in error detection. EIP-55 adds a checksum without changing the characters. Compute Keccak-256 of the lowercase address written as text. For each letter in the address, write it in uppercase if the matching hexadecimal digit of that hash is 8 or more, and in lowercase otherwise. Digits do not change. Software that knows the rule can detect most typing mistakes. Software that does not know it still reads the address, because hex is not case sensitive.

3. Five concepts to keep apart

ConceptMeaningWhere it appears
Key generationCreating new secret randomness from a random source. The result is unpredictable.The entropy at the start of BIP-39.
Key derivationComputing keys deterministically from existing secret data. The same input always gives the same output.PBKDF2 for the seed, BIP-32 and BIP-44 for the tree of keys.
Public-key cryptographyA key pair where the public key can be shared and the private key cannot be recovered from it. Used for signatures.secp256k1, Q = kG.
HashingA function from any input to a fixed-size output, meant to be one-way, with no secret key.Keccak-256 for the address. SHA-256 and SHA-512 inside BIP-39 and BIP-32.
ChecksumA small value added to detect accidental errors. It does not give secrecy or protect against an attacker.The 4 or more checksum bits in BIP-39, and the letter case in EIP-55.
EncodingA reversible change of representation, with no secrecy.Words for bits in BIP-39, hexadecimal and the 0x prefix for the address, and the case pattern in EIP-55.

One step can belong to more than one category. Hashing is used to build a checksum, and EIP-55 is both a checksum and an encoding. The important point is that only generation introduces new randomness, and only derivation and hashing are deterministic.

4. Historical context

YearItemNote
1977RSAFirst widely used public-key system, based on factoring. Elliptic curves came later and give the same security with much shorter keys.
2001SHA-2 / SHA-512NIST hash family. SHA-512 is used inside PBKDF2 and HMAC in BIP-39 and BIP-32.
2012BIP-32Hierarchical deterministic wallets. In the same year Keccak won the NIST SHA-3 competition.
2013BIP-39Mnemonic code for generating deterministic keys.
2014BIP-44Multi-account, multi-coin derivation paths.
2015SHA-3 (FIPS 202)NIST standard based on Keccak. Ethereum launched in 2015 using the original Keccak, before the standard was finalized.
2016EIP-55Mixed-case checksum for Ethereum addresses.

The order matters for understanding the choices. The Bitcoin-derived wallet standards (BIP-32, 39, 44) rely on SHA-2, which was already established. Ethereum chose Keccak because it was the winner of the SHA-3 competition at the time, and kept the original version after NIST changed the padding in the final standard.

5. SHA-2 / SHA-512 versus Keccak / SHA-3

Both are cryptographic hash functions, but they have different internal designs. SHA-2 uses the Merkle–Damgård construction. Keccak uses a sponge construction built on a permutation of a 1600-bit state, which absorbs the input and then squeezes out the output. The two are not variants of each other.

Keccak is the design chosen for SHA-3. The standardized SHA3-256 and the Keccak-256 used by Ethereum share the same permutation but differ in the padding: NIST added a domain-separation suffix, so the two functions produce different outputs for the same input. For the empty string, for example, Keccak-256 gives c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470 and SHA3-256 gives a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a. Using a library function called "sha3_256" instead of Keccak-256 is a common mistake when computing Ethereum addresses.

6. Why several techniques are used

Each step solves a different problem, and no single algorithm solves all of them.

  • BIP-39, BIP-32, BIP-44 (key management and derivation): one short backup, written as words, regenerates every key in a predictable structure. A hash or a curve alone does not give a tree of accounts or a readable backup.
  • secp256k1 (public/private relationship and signatures): only a public-key system lets anyone verify a signature without learning the secret. A hash function has no such asymmetry.
  • Keccak-256 (hashing): compresses the public key into a short fixed-size address and has no algebraic structure that can be exploited.
  • EIP-55 (checksum and error detection): protects the user from typing mistakes. It is not meant to provide security against attackers.

Using one algorithm for everything would also force compromises, such as making a hash function reversible or giving a signature scheme no structure. Separating the roles lets each primitive be replaced or analyzed on its own. Each step also has a distinct failure mode, so the weakness of one does not automatically break the others.

7. Statistical properties

  • Entropy and mnemonic: the strength of the wallet comes from the entropy, 128 or 256 bits from a cryptographically secure random generator. The 4-bit checksum of a 12-word phrase means that only 1 in 16 random combinations of words is valid, so it detects mistakes but adds no security.
  • Seed and derived keys: PBKDF2-HMAC-SHA512 and HMAC-SHA512 produce outputs that are computationally indistinguishable from uniform random bytes for someone without the input. The 2048 iterations only slow down guessing of weak passphrases.
  • Private key range: a private key must lie between 1 and n−1. Since n is very close to 2256, a random 256-bit value falls outside that range with probability about 2−128, which is negligible.
  • Public key: the coordinates of kG look irregular, but they are structured. The relation (a+b)G = aG + bG holds, so scalar multiplication is a one-way function without the avalanche and collision properties of a hash, as shown in homework 1.
  • Keccak-256: these are the properties specific to hash functions. A change of one input bit should flip about half of the 256 output bits (avalanche), outputs should look uniform, and finding a collision should take about 2128 operations by the birthday bound. The address keeps only 160 bits, so a collision costs about 280 operations and a second preimage about 2160.
  • EIP-55: an address has on average about 15 letters, each carrying one checksum bit. A random typo is therefore detected with probability roughly 1 − 2−15, about 99.997%.

Uniformity and avalanche are meaningful for the hash and for the pseudorandom derivation steps. For secp256k1 the meaningful property is the hardness of the discrete logarithm. Statistical tests on outputs can show that something is poorly designed, but they cannot prove that something is secure.

8. Observing the pipeline in a wallet

A wallet such as MetaMask, Rabby, Exodus or Rainbow makes the pipeline visible. These are the observations that map to each step. Use a new wallet with no funds, and never share the recovery phrase.

  • Creating a wallet shows a 12-word recovery phrase: the BIP-39 mnemonic.
  • Restoring the same phrase in another wallet program gives the same addresses: derivation is deterministic and the paths follow BIP-44.
  • Adding a second account gives a new address from the same phrase: the last element of the path changes.
  • Adding a passphrase when restoring (where the wallet supports it) gives a different set of addresses: the passphrase is part of the PBKDF2 salt.
  • The address is shown with a mix of uppercase and lowercase letters: EIP-55. Changing the case of one letter makes many tools report an invalid checksum.

9. Conclusion

The Ethereum wallet pipeline combines primitives with different jobs. BIP-39, BIP-32 and BIP-44 handle key management and derivation from a single backup. secp256k1 provides the public/private key relationship and signatures. Keccak-256 compresses the public key into an address, and EIP-55 adds error detection to its written form. The pipeline works because each step is deterministic and well defined, with randomness introduced only once, at the generation of the entropy. The result is a system where a short phrase is enough to recover every key, while the secret cannot be computed from the public data.
