1. The toy ECC scheme: main steps and the role of the keys

  
The scheme is an ElGamal/ECIES-style hybrid on secp256k1 (G is the standard base point, group order n ≈ 2²⁵⁶). The only toy parts are the small private-key range and a simple key-derivation step.

  
    
    
  1. Key generation (receiver). Choose the private key k in 1 … 2^bits (a real system would use 1 … n−1). The public key is Q = kG. Only k must stay secret.
    2. 
    
  2. Encryption (sender). Pick a fresh random ephemeral scalar r and compute C1 = rG. Compute the shared secret S = rQ. Derive a keystream from the x-coordinate of S and XOR it with the message bytes. The ciphertext is (C1, bytes).
    3. 
    
  3. Decryption (receiver). Compute S' = kC1 = k(rG) = r(kG) = rQ = S, rebuild the same keystream and XOR again.
    4. 
  

  
Roles: k is the long-term secret that only the receiver holds; Q is public and lets anyone encrypt; r is a one-time secret of the sender that is discarded after encryption; S is a Diffie-Hellman shared secret that neither side transmits. Security rests on the fact that computing S from Q and C1 requires solving the (computational) Diffie-Hellman problem, which is believed to be as hard as the ECDLP for large groups. The scheme is asymmetric: the encryption key (Q) and the decryption key (k) differ.

Both schemes use a secret that is combined with the message in an invertible way, and both are reversible by the right key. They differ in the key type (shared versus public/private), in the size of the key space, and mostly in the statistics: Caesar preserves the statistics of the language, the ECC scheme hides them behind a keystream.


  
3. Cryptanalysis of the Caesar cipher: algorithm, tests, limits

  
The attack in Part C builds a model of English from the corpus: unigram frequencies f(a) and bigram probabilities P(b|a). For each of the 26 candidate keys it decrypts the ciphertext and scores the result. Three methods are compared:

  
    
    
  • Peak matching: the most frequent ciphertext letter is assumed to be the most frequent letter of the corpus (E). Cheap, but it only uses one value of the histogram.
    • 
    
  • Letter-frequency analysis (χ²): choose the shift that minimizes Σ (observed − expected)² / expected over all 26 letters.
    • 
    
  • Bigram (n-gram) scoring: choose the shift that maximizes the log-likelihood of the decrypted letter pairs. This also acts as exhaustive key search with an automatic judge, because all 26 keys are tried.
    • 
  

  
Behaviour to read from the table in Part C (one run, 300 trials per length; your numbers will differ by a few points): with 5 letters the success rates were about 17% (peak matching), 45% (χ²) and 64% (bigrams); with 10 letters about 22%, 79% and 92%. χ² is practically always right from 40 letters and bigram scoring from 20 letters, while peak matching needs about 160 letters to reach 90% and 320 to be reliable. Bigram scoring is the best on short texts because it uses 676 values instead of 26. A caveat on the experiment: the test text has only about 660 letters, so the random windows overlap and the 300 trials are not independent; the percentages are indicative, not precise estimates. Limits: letters are extracted after removing spaces and punctuation, so some bigrams in the model straddle word boundaries (for example the last letter of one word and the first of the next); a model built inside words only would be more accurate, and the ciphertext used in the attack is treated the same way, so the model and the data are consistent. The language must match the corpus (here the opening of a nineteenth-century novel, close to modern English but with its own vocabulary); the plaintext must not be atypical (for example a text with few E's); very short messages such as the default message (33 letters) can have several shifts that look plausible. Exhaustive search is always possible here, since there are only 26 keys, and a human can read the right candidate, which statistics alone cannot do reliably for very short texts.

In practice the last three are exhaustive search plus a different scoring function: the 26 keys are always enumerated, and what changes is the quality of the judge. The success rates in the table of Part C show the ranking (peak matching < χ² ≤ bigrams on short texts), and all methods converge to almost 100% when the ciphertext is long. The same idea does not transfer to the ECC scheme: the judge there is exact (kG = Q), so no statistics are needed.


  
4. Attack on the toy ECC scheme and comparison with the Caesar attack

  
Because k is only in 1 … 2^bits, the attacker can compute the public key of each candidate and compare it with Q. Two attacks are implemented. Exhaustive search computes G, 2G, 3G, … until kG = Q: at most 2^bits point additions. Baby-step giant-step (Shanks) writes k = i·m + j with m = ⌈√N⌉: it stores the m "baby" points jG in a table, then walks Q − i·(mG) until it hits the table. This needs about 2·√N operations and √N memory (256 + 256 for 16 bits). Once k is known, the attacker computes S = kC1 and decrypts exactly like the receiver.

  
Differences from the Caesar attack: the Caesar attack uses statistics of the plaintext and needs a language model and enough ciphertext; the ECC attack uses only the algebra of the group, needs no corpus, works on any message (even one byte) and gives a certain answer, because kG = Q can be checked exactly. The Caesar attack gets a probabilistic answer that depends on the text length; the ECC attack depends only on the size of the key space.


  
5. Why this does not work against a properly configured ECC scheme

  
With a random private key in 1 … n−1 (n ≈ 2²⁵⁶), exhaustive search needs about 2²⁵⁶ additions, and BSGS or Pollard's rho need about 2¹²⁸ operations (BSGS also 2¹²⁸ memory). This is far beyond any feasible computation: even 10¹² operations per second would need on the order of 10²⁶ years for 2¹²⁸ steps. The cost of the attack grows exponentially with the key size while the cost of honest use grows only polynomially. Statistical tools do not help either, since the ciphertext carries no letter statistics. The only known threat of a different kind is Shor's algorithm on a large quantum computer.

Summary. The restricted key space makes the ECDLP-type attacks feasible: every attack that recovers k costs about √N or N, so shrinking the range from 2²⁵⁶ to 2¹⁶ removes the security completely. With a full-size key those attacks cost at least 2¹²⁸. The design weaknesses are independent of the size of k: the 32-bit seed caps the real security of the scheme at about 2³² work even with a perfect 256-bit key, so an attacker would choose the cheaper of the two routes, min(√N, 2³²). In the demo (N = 2¹⁶) BSGS is cheaper; with a real key the seed search would be. For this reason the scheme must not be read as a secure implementation of ECIES: the security argument of section 5 holds for the ECC problem, not for the whole toy construction. Neither weakness has an equivalent in the Caesar attack, where the single flaw is the tiny key space combined with unchanged language statistics.

  
More detail on the weaknesses by cause:

  
    
    
  • Caused by the restricted key space: the two attacks above; also a precomputed table of all public keys (a rainbow-style lookup of Q → k) would break every user of the system instantly.
    • 
    
  • Caused by the toy design, even with a full-size k: (i) the keystream is seeded with only 32 bits folded from S.x and produced by a non-cryptographic generator, so an attacker could skip the ECC entirely and try all 2³² seeds against a known or guessable plaintext; (ii) the XOR is malleable and there is no authentication, so an attacker can flip bits of the plaintext undetected; (iii) a known plaintext reveals the keystream bytes directly; (iv) a weak random number generator for r would leak S (reuse of r gives the same keystream, which is the same two-time-pad problem as in stream ciphers); (v) no padding, so the message length is visible. A real scheme (ECIES, or ECDH + HKDF + AES-GCM) fixes these with a proper KDF, an authenticated cipher and a secure source of randomness.
    • 
    
  • Not an issue here: secp256k1 has cofactor 1, so invalid-curve and small-subgroup problems do not apply to points that are checked to lie on the curve. This would matter on other curves.
